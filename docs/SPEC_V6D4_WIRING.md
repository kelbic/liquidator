# ТЗ: обвязка `chain/` под v6-D4 + деплой (задача #129), ред.1

Статус: НОРМАТИВНО. Решение kelbic 16.08: «делаем Г2д первым и 129 сразу следом».
Предмет: перевести боевую обвязку с однослотовой доски v5 на мультислот v6-D4.
Контракт принят и лежит в main (`contracts/src/LiquidatorV6.sol`, 741c34b), ТЗ контракта —
`docs/SPEC_V6D4.md` ред.4. Стенд контракта — `test_fork_v6d4.py`, 12/12.

**Что НЕ входит в предмет:** денежный путь (`_liquidate`/`onMorphoLiquidate`/ERC20) — он
скопирован из v5 бит-в-бит и уже проверен линзой; его не трогать вовсе.

---

## §0. Граница риска и порядок включения

v5 (`0x85BadE2cdD375Ab1b75f5C522B7989a12f939292`) остаётся В БОЮ до конца работ. v6 деплоится
по **новому адресу**; переключение — отдельным шагом с ручкой отката на уровне конфигурации.

Порядок, обязательный к соблюдению:

1. правка контракта §1 (остаточная дыра) + повторная приёмка затронутых пунктов;
2. деплой v6 по новому адресу, `setAuthorizedBatch` на 110 ног — **но обвязка ещё целит в v5**;
3. приёмка арма НА ЦЕПИ по новому адресу в тишине (без огня);
4. переключение адреса контракта, переподпись лестниц под новый адрес и байт `0xFF`;
5. приёмка боем.

**Между шагами 2 и 4 флот стреляет в v5 и ничего не теряет.** Шаг 4 необратим в пределах
окна: предподписанные лестницы несут адрес получателя внутри подписи, поэтому «переключить
обратно» = пересборка лестниц (≈77 с CPU). Значит откат на v5 — операция ТИХОГО времени, и
переключение делать в тишине, а не в горячем окне.

## §1. Правка контракта: остаточная дыра (обязательна ДО деплоя)

Отпечаток рынка сверяется на ЗАПИСИ указателя (`setHot`), но `setGroup`/`clearGroup` не
смотрят на живой `_hot`. Перезарядка группы ВНУТРИ живого спана новым рынком ломает инвариант
«спан = один рынок» ПОСТФАКТУМ: доля флота уходит в другой рынок. Потери средств нет — огонь
идёт по нашему же законно армленному плану этой группы, — цена в неверной раскладке плотности,
и она МОЛЧАЛИВА.

**Решение принято сессией: закрывать в КОНТРАКТЕ, а не дисциплиной обвязки.** Обоснование —
канон: гард, живущий в дисциплине вызывающего, не является гардом; он держится ровно до первой
правки обвязки, сделанной по другому поводу.

Требование:

```
error HotSpanLive();          // новая ошибка

// в setGroup(g, ...) и clearGroup(g), ПЕРЕД записью:
Hot storage h = _hot;
if (h.count != 0 && block.timestamp < h.until
    && g >= h.g0 && g < uint256(h.g0) + uint256(h.count)) revert HotSpanLive();
```

Три свойства этого решения, каждое умышленно:

* **Отказ ГРОМКИЙ, а не тихий.** Альтернатива «молча гасить `_hot`» разоружает весь флот
  посреди окна и выглядит как здоровый промах — ровно тот класс дефекта, который мы уже
  ловили (нога в протухшей группе возвращалась молча). Канон: молчаливый отказ хуже отказа.
* **`setTargets` НЕ ТРОГАЕМ.** Докладка каскада не переписывает заголовок, `mp` не меняется,
  инвариант спана цел. Это и есть штатный путь роста каскада внутри живого окна — запрещать
  его нельзя, иначе гард убьёт то, ради чего строился мультислот.
* **Горячий путь не платит ничего**: проверка стоит в `onlyOwner`-пути арма.

Обвязка со своей стороны зовёт `clearHot()` перед плановой перезарядкой группы. Это удобство,
а не гард: гард — реверт.

**Приёмка правки (парой прогонов, красный-на-базе обязателен):**

| пункт | КРАСНЫЙ (без правки) | ЗЕЛЁНЫЙ (с правкой) |
|---|---|---|
| `setGroup` в группу живого спана с ДРУГИМ `mp` | принят; часть флота уходит в чужой рынок | `HotSpanLive` |
| `clearGroup` в группу живого спана | принят; ноги спана глохнут молча | `HotSpanLive` |
| `setGroup` в группу ВНЕ спана | принят | принят (не сломали штатное) |
| `setGroup` в тот же индекс после `clearHot()` | принят | принят |
| `setGroup` в группу спана с ИСТЁКШИМ `until` | принят | принят (мёртвый указатель не запирает доску) |
| `setTargets` (докладка) в группу живого спана | принят | **принят** — и это позитивный контроль |
| огонь ≥24 ногами после разрешённой докладки | — | ликвидирует; спан цел |

## §2. Модель раскладки: кто занимает группы

v5 арбитрировал ОДИН слот по EV (гард #88). v6 даёт 8 групп × 8 целей, и правило занятия
слотов — теперь предмет обвязки, а не контракта.

**Инвариант, на котором стоит указатель:** группы одного спана несут ОДИН И ТОТ ЖЕ `mp`.
Отсюда раскладка:

* **Группа = (рынок, до 8 целей этого рынка), цели упорядочены по EV убыванием.**
* **Каскад одного рынка >8 целей** = несколько ПОДРЯД идущих групп с одинаковым `mp`
  (спан). `count` указателя = число групп спана.
* **Разные рынки одновременно** — законны в разных группах, но указатель наводится
  только `count=1` (спан из одной группы). Наводить спан на разные рынки контракт не даст
  (`mpHash`), и это правильно.

**Арбитраж при нехватке групп** (8 занято, пришёл новый рынок с большим EV): вытесняется
группа с наименьшим EV, и только если новый превосходит её на `SPEC_FIRE_V2_EV_MARGIN`
(перенос гистерезиса #88 с уровня слота на уровень группы). Живой спан не вытесняется вовсе —
он под гардом §1 и вытеснение теперь ревертит.

**Ручка концентрации.** `count` — это выбор «плотность против покрытия»: `count=1` = вся
плотность 110 ног на 8 целей одного рынка; `count=4` = каскад на 32 цели, но каждая цель
получает ~1/4 плотности. **Пока звено Г (прибытие) не решено, дефолт — `count=1`**: ёмкость,
купленная ценой плотности, в гонке за позицию не окупается. Поднимать `count` — только по
факту каскада, где целей больше, чем слотов у конкурентов.

## §3. Арм: приёмка ПО ЦЕПИ, не по хэшу

Канон закрыт кровью (#84: три недели тракт строился над пустым стораджем, 4 из 4 `setPlan`
сгорели по газу при `status=0`, а обвязка писала «доска armed» по возвращённому хэшу).

Для каждой армленной группы требуются ОБА доказательства, и оба привязаны к НАШЕЙ tx:

1. квитанция нашего хэша со `status == 1`;
2. чтение с цепи: `groupInfo(g)` → `deadline` равен НАШЕМУ `deadline` И `n` равен числу
   отправленных целей; плюс `targetInfo(g, i)` → `borrower` совпадает по КАЖДОЙ цели `i < n`.

Сверки одного `borrower` НЕДОСТАТОЧНО (хвост #84): кит держится в топе часами, переарм идёт
по той же цели, и несевший арм засчитывался бы по ПРЕЖНЕМУ плану того же заёмщика. Дедлайн
и полный список `borrower` ловят и чужой слот, и протухший.

**Цена арма измерена:** группа из 8 целей с роутом 2 КБ = **12 757 108** газа. Лимит газа
считать от этого числа с запасом, а не от лимита v5 — иначе повторяем #84 буквально.
Арм = 3.19% блока Base (gasLimit 400M); гейт секвенсера закрыт эталоном (5 чужих tx с газом
до 15.3M намайнены в 13 блоках).

## §4. Указатель: `until` берётся С ЦЕПИ

**Правило, выпавшее из гарда и пойманное стендом:** `until` указателя обязан быть ≤ минимума
дедлайнов ВСЕХ групп спана. Стенд споткнулся об это сам — просил `until` из настенных часов
длиннее армленного плана, и гард законно откатил.

Обвязка обязана считать `until` так:

```
until = min( groupInfo(g).deadline  для g в [g0, g0+count) )    # чтение С ЦЕПИ
```

Не из своих часов, не из того, что мы «отправляли» — из того, что в контракте ЛЕЖИТ.
Это же чтение даёт `mpHash`: `keccak256(abi.encode(mp))` считается от параметров рынка,
которые мы армили, и обязано совпасть — если не совпало, арм не сел, и наводить нечего.

**Бюджет горячего момента: 84 035 газа** на перецеливание при `count=4` (не 31k — это
устаревшее число до гарда отпечатка; гард стоит ≈6 SLOAD на группу спана). Против арма
12 757 108 это дешевле в 152 раза — разделение «дорого заранее, дёшево в момент» устояло.

## §5. Пробы: байт `0xFF`

Байт пробы меняется `0x01` → `0xFF` (сентинел горячего указателя). Байт запечён В ПОДПИСЬ,
поэтому смена байта = пересборка всех лестниц (см. §0, шаг 4, только в тишине).

Явный байт (`0x00`..`0x07` = индекс группы) остаётся законным путём и дешевле на 2 466 газа
(54 968 против 57 434 на промахе). Он применим там, где цель известна заранее и не меняется
в окне. **Дефолт боевых лестниц — сентинел**: статическое разбиение ног по группам делило бы
плотность на 8 ровно в том звене, которое сейчас связывает.

## §6. Заявка: дефолт `repaidShares`

`seizedAssets` — РАЗМЕН, а не улучшение. Morpho считает `repaid = seized·price/LIF`, поэтому
при фиксированном `seizedAssets` падение оракула на k делает ликвидацию ЧАСТИЧНОЙ: профит
падает пропорционально k, остаток позиции достаётся конкуренту. Заявка по `repaidShares` в
этом направлении ИНВАРИАНТНА, а направление, в котором `seizedAssets` хуже, — ровно направление
каскада.

**Дефолт — `repaidShares`** (`seizedAssets = 0`). `seizedAssets` применять точечно там, где
точность входа свопа важнее (класс #79), и каждый такой случай называть явно.

## §7. Гигиена после проигранной гонки

`clearTarget(g, i)` после подтверждённой чужой победы по этой цели. Мотив прямой: цель,
стабильно отказывающая в голове группы, в v5 стоила одного плана, в v6 стоила бы группы —
ротация старта (`keccak256(msg.sender) % n`) это смягчает, но не отменяет: труп в доске
крадёт ~1/n огня группы (замер стенда: 28 из 32 взято, 4 утонули).

Источник факта чужой победы — подписчик `Liquidate` фонового индекса цепи (#110/#123), не
наш журнал.

## §8. Что должно быть измерено, а не заявлено

Приёмка обвязки — числами с цепи, каждое с независимым эталоном:

1. **Арм сел**: для ≥1 боевой группы `groupInfo`/`targetInfo` совпали по всем `n` целям.
   Красный контроль: арм с заведомо малым лимитом газа обязан дать «не сел», а не «armed».
2. **Указатель сел и наведён верно**: `hotInfo()` = наши `g0`/`count`/`until`, и `until`
   равен минимуму дедлайнов спана, ПРОЧИТАННОМУ с цепи.
3. **Ноги стреляют в v6**: ≥1 боевой блок, где пробы от ≥N ног пришли на адрес v6 с байтом
   `0xFF`. Эталон — цепь, не счётчик обвязки (счётчик, который механизм сообщает о себе сам,
   растёт и когда механизм мёртв).
4. **Промах стоит сколько обещано**: газ промаха с боевой квитанции ≈ 57 434 (порог 58 000).
5. **Гард §1 живой в бою**: попытка `setGroup` в живой спан обязана дать `HotSpanLive` в
   боевой конфигурации, а не только на стенде.

**Пункт, который нельзя сдать самоотчётом:** «обвязка целит в v6». Доказательство — адрес
получателя в боевой tx на цепи.

## §9. Хвост: вторая половина #81

Два armed-плана в одном пуле не независимы: `minOut` второго посчитан ДО свопа первого.
В v5 это было теоретично (один слот — один план). **В v6 это становится боевым**: группа из
8 целей одного рынка — это ровно 8 планов в одном пуле. Порядок исполнения задаёт ротация,
то есть предсказать, чей своп идёт первым, нельзя.

Требование: `minOut` каждой цели группы считать с запасом на исполнение ПРЕДЫДУЩИХ целей той
же группы по тому же пулу (худший случай: все n−1 прошли раньше), либо явно назвать и
записать в пределы, что группа собирается только из целей с непересекающимися пулами.
Молчаливое наследование v5-логики здесь — дефект по построению.
