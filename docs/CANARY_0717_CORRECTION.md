# CANARY 07-17 — ПОПРАВКА К РЫЧАГУ (верификация по коду main@9149efa)

> Правит две вещи в срезе 07-17 (HANDOFF) и в STATE.md. Вывод канарейки о СЕГМЕНТЕ верен;
> названный РЫЧАГ — почти пустой. Проверено 3 независимыми разборами кода + синтез.

## Что подтвердилось (не трогать)
- **Сегмент правильный, барьер — скорость САБМИТА, не fee.** Победители 25-30 при tip ~0.5 gwei.
  Наш tip 6 gwei против них — переплата (приходим в более поздний флешблок, fee не компенсирует).
- **Разрыв даже ШИРЕ +46:** медиана +46 считается ТОЛЬКО по попаданиям в блок; 37% промахов
  (+1 блок = полный проигрыш) в медиану не входят (`hotpath.py:821/824`). Честная медиана хуже +46.

## Что ОПРОВЕРГНУТО: «убрать prepare_fast» — не рычаг
- **`prepare_fast` уже zero-RTT** (`hotpath.py:747-778`): params из `_FULL_PARAMS_CACHE`, state от
  caller, `direct_swap` = локальный ABI-encode, fee из fb-хедера, gas из кэша. Цена — только Python-CPU
  (микросекунды), НЕ ~130мс. Убрать = сэкономить микросекунды.
- **«Полный in-memory флип / слой 2» — НЕ нетронутый рычаг.** Слой 1 (feed-цена, 0 RTT) и слой 2
  (`read_positions_cached`, 0 RTT) УЖЕ в бою; пол +46 измерен ИМЕННО с ними. Это содержимое +46, не апгрейд.
- Канарейка стреляет в `if not ready:` (`hotpath.py:991`) — после гейта цены + read + `_flips`,
  включает sign+send. На send-оси она даже ПЕССИМИСТична (не шлёт fb-fee → +2 Alchemy-RTT; пропускает
  SEND-3 raw-броадкаст). Т.е. её оптимизм = ровно исключённый prepare, частично гасится медленным send.

## Где на самом деле сидит +46
1. **Сеть (доминанта):** WS-инжест + brotli/JSON-декод транслята (публичный Flashblocks WS) + RTT
   отправки к секвенсеру.
2. **`_flips` по всему набору** (~1400 борроверов cbBTC, не пруненный) — CPU внутри пола (`hotpath.py:194-206`).
3. **Остаточный preconf-RTT** для рынков того же agg с oracle≠hint_oracle (`hotpath.py:906-909`).

## Порядок шагов (по цене/уверенности)
1. **СНАЧАЛА доизмерить (бесплатно):** разложить существующий `DIAG timing read=/sim=/send=` на
   реальных prep → сколько мс в детекте/read/flips/send. + правка канарейки: медиана ВКЛЮЧАЯ
   MISSED-BLOCK (или % промахов) и tx-count блока в `_canary_measure` (сейчас «поз→мс ~130-230» кодом
   НЕ обоснован). Решает, куда тратиться, ДО траты.
2. **Дёшево (код, без инфры), если п.1 покажет CPU/RTT там:** прун `_flips` до near-threshold +
   убрать остаточный `price_fn`-RTT (`hotpath.py:194-206, 906-909`).
3. **Дорого (инфра), вероятно доминанта:** отправитель в тот же AWS-регион/AZ, что секвенсер Base
   (инкремент P2-11 после Charlotte 30мс → single-digit ms). НЕ начинать, пока п.1 не подтвердит,
   что send-RTT доминирует — самый дорогой и трудно-обратимый шаг.
4. **Удаление `prepare_fast`** — держать как микро-CPU-оптимизацию, НЕ как основной рычаг.
