# ТЗ: боевой контракт v6-D4 (мультислот)

Статус: спека сессии (Fable) от 15.08, реализация — агентом. Дизайн выбран ЧИСЛАМИ в
репетиции Г1б-1 (см. STATE «15.08: Г1б-1 форк-репетиция ЗАВЕРШЕНА»), гейт (2) пройден боем
(блок 50012719, 368/368 проб на tip транзита). Прототип-ПРИБОР: `contracts/src/LiquidatorV6Probe.sol`
(контракт `LiquidatorV6D4`), замер: `test_fork_gas_multislot.py`.

**Что v6 меняет и что НЕ меняет.** Снимает потолок «один слот = одна цель»: в каскаде
контестится до 64 целей вместо 1. Гонку он НЕ выигрывает — прибытие/плотность (звено Г)
остаётся открытым и решается отдельно.

## 1. Раскладка D4

`G=8` групп (одна группа = один рынок), в каждой `M=8` целей ⇒ 64 цели.

```
struct Target {                      struct Group {
    address borrower;                    MarketParams mp;
    uint128 repaidShares;                uint256 gateTrigger;   // = max персональных порогов
    uint128 seizedAssets;   // К1           uint64 deadline;
    address swapTarget;                     uint8  n;
    bytes   swapCallData;            }
    uint256 minProfit;               Group[8] internal _groups;
    address unwrapTarget;            mapping(uint256 => Target[8]) internal _targets;
    uint256 triggerPrice;            Hot internal _hot;
}
```

Группы индексуются НАМИ: ничто не обязывает их быть разными рынками — каскад на 26 целей
одного рынка законно занимает 4 группы по 8 целей с одинаковым `mp`.

## 2. Три решения сверх прототипа (обоснование — обязательная часть ТЗ)

### 2.1. Горячий указатель вместо байта-адресата (ГЛАВНОЕ)

Прототип берёт группу из байта пробы. В бою это **делит плотность на G**: пробы
ПРЕДПОДПИСАНЫ, байт запечён в подпись, а перецелевание = пересборка лестниц. Цена
пересборки: 110 ног × глубина 32 × ~22мс подписи ≈ **77 с CPU** — в момент открытия окна
это невозможно (аудит #127 размазывает пересборку на ~22 прохода фоном). Статическое
разбиение ног по группам делит плотность на 8 ровно в том звене (прибытие), которое сейчас
и есть связывающий предел. Поэтому:

- Байт пробы = **сентинел `0xFF`** ⇒ группа берётся из стораджа `_hot`.
- `_hot = {uint8 g0, uint8 count, uint64 until}` — ОДИН слот. **ЗАМЕРЕНО, две поправки к моим
  оценкам.** (1) Оценка ред.1 «~5k» была про SSTORE, а не про tx: голая перестановка стоила
  31 003 газа с квитанции. (2) После гардов §2.5б цена выросла — проверка отпечатка и дедлайна
  каждой группы спана это ≈6 SLOAD на группу: **перецеливание при `count=4` = 84 035 газа**
  (первая запись 61 887). Против арма группы 12 757 108 это дешевле в **152 раза**, разделение
  «дорого заранее, дёшево в момент» устояло, но **бюджет горячего момента считать по 84k**.
  Пред-армим группы заранее (дорого, в тишине), в горячий момент перенаправляем весь огонь.
- При `count > 1` группа = `g0 + uint160(msg.sender) % count` — ноги детерминированно
  расходятся по спану групп БЕЗ пересборки лестниц. `count` — рантайм-ручка «концентрация
  против покрытия»: `1` = вся плотность на один рынок, `4` = каскад на 32 цели.
- Байты `1..8` (явная группа) остаются — для дрелей, движкового прямого огня и хеджа.

Цена: +1 SLOAD (~2100 газа) на промах ⇒ ~57k против 54.9k. В кап $100/сут влезает
($57-71 против $55-68).

**Гарды (незнание закрывает):** `count == 0` → return; `until <= block.timestamp` → return;
`g0 + count > 8` → return. Байт `0x00` и `9..0xFE` → return (случайный нулевой байт не
должен стрелять). `msg.data.length == 0` → return; `> 1` → revert (как в v5).

### 2.2. Дефект прототипа: неизвестная цена запирает огонь

В `LiquidatorV6D4.fallback` прототипа `px` инициализирован `type(uint256).max`, и
персональный фильтр — `if (t != 0 && px > t) continue;`. Следствия:
- оракул ревертнул (`catch {}`) ⇒ `px` остаётся max ⇒ **пропускаются ВСЕ цели** с личным
  порогом — тихий no-op там, где v5 стреляет (v5: «оракул сломан → фильтр выключен, решает
  Morpho»);
- `gateTrigger == 0` («фильтра нет») ⇒ оракул не вызывается ⇒ тот же max ⇒ **«фильтр
  выключен» означает «никогда не стрелять»** — переворот семантики v5 fail-open.

В боевом v6 цена несёт признак известности (`bool pxKnown`); личный порог применяется
ТОЛЬКО при `pxKnown`. Неизвестная цена = фильтр выключен = пробуем (Morpho — авторитет
ликвидируемости, триггер только газовый фильтр). Оба случая — обязательные тесты §5.

### 2.3. К1: параметризация `seizedAssets` (закрывает класс #79/#81)

Morpho требует ровно один из `seizedAssets`/`repaidShares` ненулевым. Заявка по
`seizedAssets` делает вход свопа ТОЧНЫМ по построению: сколько коллатерала придёт — известно
до подписи calldata, поэтому запечённая сумма свопа всегда верна.

**ПОПРАВКА ред.3 (линза, 15.08): это РАЗМЕН, а не строгое улучшение — моя формулировка ред.1
«плавает только repaid, вниз, т.е. по направлению каскада безопасно» была половиной анализа
и в этой редакции запрещена.** Morpho считает `repaid = seized·price/LIF`, поэтому при
фиксированном `seizedAssets` падение оракула на k превращает ПОЛНУЮ ликвидацию в ЧАСТИЧНУЮ:
гасится доля k долга, профит падает пропорционально k, остаток позиции остаётся живым — и
достаётся конкуренту. Заявка v5 по `repaidShares` в этом же направлении дрейфа ИНВАРИАНТНА
(repaid фиксирован, seize растёт, профит ≈ repaid·(LIF·(1−slip)−1) от цены не зависит).

Итого: направление, в котором `seizedAssets` ХУЖЕ, — это ровно направление каскада (падение
цены), а взамен закрывается класс #79 (пыль несвопнутого коллатерала из-за неточного входа).
**Контракт обязан уметь ОБА входа, выбор — решение обвязки, а не константа контракта.**
Дефолт остаётся `repaidShares`; `seizedAssets` берётся там, где точность входа свопа важнее
инвариантности к падению цены. Это записывается в известные пределы именно так.

- `Target` несёт оба поля упакованными в один слот (`uint128` каждое); ровно один ненулевой
  — проверку делает Morpho, мы пробрасываем.
- Внешняя `liquidateEx(mp, borrower, seizedAssets, repaidShares, swapTarget, swapCallData,
  minProfit, unwrapTarget)`; **`liquidate(...)` с ABI v5 (7 аргументов) сохраняется** как
  обёртка с `seizedAssets = 0` — обвязка бота и `batchLiquidate` не ломаются.
- `#81` (minOut второго плана посчитан до свопа первого) контрактом закрывается лишь
  наполовину: авторитет проскальзывания — НАШ (`profit >= minProfit` и `CannotRepay`), а не
  minOut роутера. Вторая половина — бот-сайд (роутерный minOut ослабить, порог держать
  `minProfit`); в этот пакет НЕ входит, остаётся в бэклоге #81.

### 2.4. Ротация старта цикла огня (добавлено 15.08 по находке стенда)

Стенд доказал (§5.7): цель, которая стабильно ОТКАЗЫВАЕТ, стоя в голове группы, запирает
всю группу. Порядок §4 даёт «одна проба = одна попытка», а отказавшая цель НЕ гасится (так и
надо: «здоровый» реверт Morpho — штатный случай, гасить план по нему нельзя, это семантика
v5). Следствие: каждая проба снова упирается в голову за 176k газа, цели 1..7 недостижимы до
ручного `clearTarget` владельца. **В v5 это стоило одного плана, в v6 стоит группы из восьми
— то есть ровно тот потолок ёмкости, ради снятия которого v6 и строится, возвращается через
путь отказа.**

Фикс — БЕЗ состояния и без учёта (счётчик отказов на денежном пути запрещён каноном «учёт
никогда не стоит перед деньгами»): цикл огня стартует не с нуля, а со смещения ноги, обход
кольцевой на всю длину `n`. Механизм уже проверен в приборе (D3 использует `start` из байта).

**ИСПРАВЛЕНИЕ ред.3 — моя ошибка ред.2, доказана линзой исполнением байткода.** Я задал
`start = uint160(msg.sender) % n` при том, что группа спана берётся ИЗ ТОГО ЖЕ вычета
(`g = g0 + uint160(msg.sender) % count`). Два вычета одного числа коррелированы: при
`gcd(count, n) > 1` группа видит лишь `n/gcd` стартовых индексов. Замер на боевом байткоде
(40 ног, 8 групп × 8 целей, пробы `0xFF`): `count=8` → каждая группа атакована РОВНО в одну
цель, покрытие 8 из 64; `count=4` → 2 старта из 8, покрытие 8 из 32; `count=1` и явный байт →
8 из 8. То есть **во флагманской конфигурации (каскад, `count>1`) ротация не давала ничего**,
и «голова съедает ≈1/n флота» на деле означало 1/2 при `count=4` и 1/1 при `count=8` — а
отказ (труп: цель уже забрал конкурент — 30 случаев из 43 по нашей истории) есть
ГОСПОДСТВУЮЩИЙ случай.

Требуется РАЗВЯЗКА источников: `start = uint256(keccak256(abi.encodePacked(msg.sender))) % n`.
Хэш, а не сдвиг битов: сдвиг развязывает только текущую пару вычетов, а хэш устойчив к любой
будущей перекройке семантики `count`. Цена ~50 газа и только на пути ОГНЯ (на промахе цикл не
исполняется), против 176k, которые стоит одна проба, утонувшая в трупе.

- На господствующем пути (промах по цене) цикл НЕ исполняется вовсе ⇒ **цена промаха не
  меняется**; ротация платится только на пути огня.
- Покрытие не теряется: нога обходит всё кольцо, поэтому единственная ликвидируемая цель
  находится любой ногой.
- Отказывающая голова съедает пробы только той доли флота, что стартует на ней (≈1/n), а не
  всего флота.
- Побочно даёт то, что каскаду и нужно: 110 ног детерминированно расходятся по 8 целям
  группы, а не долбят цель №0.

### 2.5. Гарды пути АРМА (ред.3, по находкам линзы)

Обе дыры ниже — на пути арма, а не промаха: гарды там стоят десятки газа и цену пробы не
двигают. Обе доказаны линзой исполнением, а не рассуждением.

**(а) Воскрешение целей прошлого арма (БЛОКЕР).** `setGroup` намеренно не затирает цели за
`ts.length` (экономия газа на слотах, которые цикл огня не читает — он ограничен `n`), а
`setTargets` расширяет `n` без проверки непрерывности. Комбинация оживляет цели предыдущего
плана под НОВЫМ заголовком: перезарядили группу двумя целями (`n=2`), доложили каскад с
`from=4` (`n=5`) — и 20 из 40 ног ушли в цели прошлого рынка с его протухшим роутом, причём
ни события, ни `targetInfo` этого не показывают. Фикс: `setTargets` требует `from <= gr.n`
(дыра запрещена), иначе `TooManySlots`.

**(б) Указатель без признака цели (мажор → гард).** `setHot` перенаправляет 110 ног по
ГОЛОМУ индексу группы: одна ошибка в байте `g0` уводит весь флот в другую, законно армленную
и не протухшую группу, а гард на чтении проверяет только span и TTL. Фикс — отпечаток рынка
в подписи: `setHot(g0, count, until, bytes32 mpHash)`, и контракт для КАЖДОЙ группы спана
`g ∈ [g0, g0+count)` требует
- `keccak256(abi.encode(gr.mp)) == mpHash` — иначе `TooManySlots`/`BadDeadline`;
- `gr.deadline >= until` — группа обязана пережить сам указатель.

Это закрепляет смысл спана: **span = ОДИН рынок, разложенный на несколько групп** (каскад
>8 целей), а прицел в разные рынки делается `count=1`.

**Боевое правило, выпавшее из гарда (не деталь теста):** `until` указателя обязан быть ≤
минимума дедлайнов групп спана. Стенд споткнулся об это сам — просил `until` из настенных
часов, длиннее уже армленного плана, и гард законно откатил tx. Обвязка обязана брать `until`
С ЦЕПИ (минимум `groupInfo().deadline` по спану), а не из своих часов.

**ОСТАТОЧНАЯ ДЫРА, найдена сессией при чтении диффа ред.3 — закрывается в пакете ОБВЯЗКИ, не
контракта.** Отпечаток сверяется на ЗАПИСИ указателя, но `setGroup`/`clearGroup` не смотрят на
живой `_hot`: перезарядка группы ВНУТРИ живого спана новым рынком ломает инвариант постфактум,
и доля флота уходит стрелять в другой рынок. Потери средств нет — огонь идёт по НАШЕМУ же
законно армленному плану этой группы (fallback берёт `mp` из самой группы), цена — неверная
раскладка плотности. Но полагаться тут на дисциплину обвязки нельзя (канон «незнание обязано
закрывать гард»), поэтому в пакет обвязки входит ОДНО из двух: либо `setGroup`/`clearGroup`
гасят `_hot`, если `g` попадает в живой спан, либо обвязка обязана звать `clearHot()` ПЕРЕД
любой перезарядкой группы спана. Пока v6 не в бою, риск нулевой. Побочно закрывается отдельная
находка: нога, попавшая в мёртвую/протухшую группу внутри спана, возвращалась МОЛЧА и
неотличимо от здорового промаха (при `count=4` разоружение одной группы тихо гасило четверть
огневой мощи) — теперь такой спан невозможно и установить, а истечь внутри TTL он не может
по второму условию.

**(в) Мелкое, туда же:** `setTargets` на группе с `deadline == 0` или протухшим исполняется
успешно и эмитит `PlanSet` — квитанция говорит «арм сел», а группа выстрелить не может
(канон «хэш tx — не эффект»). Требовать живой заголовок: `deadline > block.timestamp`.
И согласовать границы TTL: сейчас указатель мёртв при `until <= now`, а группа ещё жива при
`now == deadline` — два соседних гарда одного смысла обязаны читаться одинаково.

## 3. Интерфейс

Арм и управление (`onlyOwner`):
- `setGroup(uint256 g, MarketParams mp, uint64 deadline, uint256 gateTrigger, Target[] ts)` — заголовок + цели.
- `setTargets(uint256 g, uint8 from, Target[] ts)` — перезапись диапазона целей без заголовка (докладка каскада).
- `setHot(uint8 g0, uint8 count, uint64 until, bytes32 mpHash)` — дешёвый горячий указатель;
  проверяет отпечаток рынка и `deadline >= until` у КАЖДОЙ группы спана (§2.5б).
- `clearHot()`, `clearGroup(uint256 g)`, `clearTarget(uint256 g, uint256 i)`.
- `setAuthorized(address, bool)` (как в v5) + `setAuthorizedBatch(address[] who, bool ok)` —
  110 ног авторизуются одной-двумя tx, а не 110.
- `setOwner`, `sweep` — из v5 без изменений.

Чтения (приёмка арма ведётся по цепи, не по хэшу — канон «хэш tx не эффект»):
- `groupInfo(g) -> (address oracle, uint64 deadline, uint256 gate, uint8 n)`
- `targetInfo(g, i) -> (address borrower, uint128 repaidShares, uint128 seizedAssets, uint256 triggerPrice)`
- `hotInfo() -> (uint8 g0, uint8 count, uint64 until)`

События: `Liquidated`, `PlanSet(uint64 deadline)`, `PlanExecuted(address indexed borrower,
uint256 profit)`, `PlanFailed(bytes4 reason)`, `SwapInput(uint256)`, `AuthorizedChanged`,
`OwnerChanged`, `BatchItemFailed` — семантика v5. Новое: `HotSet(uint8 g0, uint8 count,
uint64 until)`. Событий, раскрывающих цель на арме, не добавлять (v5: «намеренно
бессодержательные»).

## 4. Порядок в fallback (порядок = цена; менять нельзя)

```
len==0 -> return ; len>1 -> revert
байт -> группа (0xFF: _hot + гарды; 1..8: явная; иначе return)
gr.deadline: 0 или прошло -> return
msg.sender не owner и не authorized -> return
gate != 0 -> oracle.price():
      p > gate -> return          // KB-планы из стораджа НЕ копируются
      иначе px = p, pxKnown = true
   catch -> pxKnown = false        // фильтр выключен, НЕ запрет (§2.2)
n == 0 -> return
start = keccak256(msg.sender) % n        // §2.4 ред.3: РАЗВЯЗАН с вычетом группы; кольцевой обход
цикл k in 0..n-1, i = (start + k) mod n:
   borrower == 0 -> continue
   pxKnown && t != 0 && px > t -> continue
   Target memory tg = ts[i]        // копия KB-байтов ТОЛЬКО здесь
   try this.liquidate(Ex) -> delete ts[i]; emit PlanExecuted; return
   catch -> emit PlanFailed(bytes4); return     // односрельность: одна проба = одна попытка
```

Односрельность: гаснет ТОЛЬКО отстрелянная цель; заголовок группы и остальные `n-1` целей
остаются живыми для следующих проб (эталон проверки — СЫРОЙ сторадж, не view).

## 5. Приёмка (форк Base, позитивный контроль ПЕРВЫМ, газ — с КВИТАНЦИИ)

1. **Позитивный контроль**: настоящая ликвидация на форке проходит насквозь через v6 —
   `Liquidated` + `Morpho.Liquidate` + профит на квитанции. Без него остальные числа не читать.
2. **Промах O(1)**: явный байт ≤ 55 200 газа (паритет с прототипом 54 906); горячий указатель
   ≤ 58 000. Мерить при G=8, M=8 (64 цели армлены) — число не должно зависеть ни от G, ни от M.
3. **Односрельность**: выстрел по цели #3 из 8 снимает РОВНО её (сырой сторадж), 7 живы, и
   следующая проба исполняет следующую цель (не тихий no-op).
4. **Спан горячего указателя**: `count=4` разводит ноги по 4 группам детерминированно;
   `count=0` / протухший `until` / `g0+count>8` — огня НЕТ.
5. **Fail-open (§2.2)**: (а) оракул реверти́т при `gate!=0` — попытка ИДЁТ; (б) `gate==0` —
   попытка идёт; в обоих случаях личный порог не запирает. Контроль негативный: при
   `pxKnown` и `px > t` цель законно пропускается.
6. **К1**: заявка по `seizedAssets` даёт вход свопа, РАВНЫЙ запечённому в calldata (сверка
   `SwapInput` с ожиданием до единицы); `liquidate(...)` со старым ABI работает как раньше.
7. **Отказ говорящий**: неудача цели эмитит `PlanFailed` с 4 байтами причины, а не тишину (#70).
8. **Авторизация**: неавторизованный отправитель — тихий no-op (не revert, гриферы не жгут план);
   `setAuthorizedBatch` реально ставит флаги (чтение с цепи).
9. **Ротация (§2.4) — ТОЛЬКО в БОЕВОЙ конфигурации.** Прежняя редакция пункта проверяла
   ротацию ЯВНЫМ байтом при `n=3` — то есть ровно там, где корреляции вычетов нет, и выдала
   «ПРОШЁЛ» на свойстве, которого в бою не было. Теперь обязательна конфигурация боя:
   сентинел `0xFF`, `count=4`, `n=8`, ≥40 ног. Требования: (а) в КАЖДОЙ группе спана жертву
   берут ноги с **≥5 различными стартовыми индексами** (при развязке ожидается ~8, при
   корреляции было 2); (б) при `count=8` покрытие целей = 8 из 8 в группе, а не 1 из 8;
   (в) труп в цели №0 не запирает группу — живые цели берутся без `clearTarget`; (г) контроль
   неизменности: **цена промаха не сдвинулась** (цикл на промахе не исполняется).
   Красный-на-базе обязателен: тот же тест на коде ред.2 обязан ПРОВАЛИТЬСЯ.
10. **Воскрешение целей (§2.5а)**: последовательность `setGroup(8 целей)` → `setGroup(2 цели)`
   → `setTargets(from=4, …)` обязана ОТКАЗАТЬ; парный позитив — непрерывная докладка
   `from = gr.n` проходит и цель достижима. Красный-на-базе: на коде ред.2 тот же сценарий
   уводит долю флота в цели прошлого плана (линза намеряла 20 из 40).
11. **Отпечаток указателя (§2.5б)**: `setHot` с `mpHash` чужого рынка — ОТКАЗ; с группой
   спана, чей `deadline < until`, — ОТКАЗ; корректный спан одного рынка — проходит и стреляет.
   Парный позитив обязателен у каждого негатива.

Стенд — в идиоме `test_fork_gas_multislot.py` (anvil-форк Base, реальный рынок, газ с
квитанций). Дефекты самого прибора считать наравне с дефектами продукта (канон «красный
стенд — не диагноз»); значение, которое прибор сообщает о себе сам, приёмкой не является.

## 6. Что остаётся НЕ закрытым этим пакетом (называть честно)

- Оффчейн-сборка M котировок на арм (латентность арма, не газ) — не измерена.
- Примет ли БОЕВОЙ секвенсер tx арма ~12.75M газа / 19 КБ (anvil принимает что угодно).
- Цена огневого окна при большом флоте (~171k газа на проигравшую пробу).
- Вторая половина #81 (роутерный minOut) — бот-сайд.
- **Win-rate ничем из этого не двигается**: v6 снимает потолок ёмкости, гонку выигрывает
  прибытие (звено Г).
